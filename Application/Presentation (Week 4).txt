Now, I wanna show how I implemented these in code. 


Firstly I created the app directory. 
In this directory backend and frontend parts are seperate.
I opened two terminal. 
One of them in backend. 
Other one in frontend.
I created virtual environment and download necessary packages and libraries to use React, FastAPI and other tools.


In backend directory, everything is located in the appropriate folder. 
I have a enum which defines the roles of users

In models directory, we define the tables, their columns and relationship with necessary restrictons in database.  
We have 4 model. 
User keeps informations of the users. 
Poll model keeps the question and relationships of the choices.
Choice model keeps the choice text. They use poll_id to match the question. 
And vote model Works same as choice and poll relationship.


The files in the routers folder contain the operations performed on the models. 
For example, the auth_router file contains the register and login functions. 
When we click the register button, a request is sent to this section, and the function first checks whether the username exists. 
It then encrypts the password using a hash algorithm and stores this information in the database. 
It then generates a token. What is a token? It's the user's ID in the application. 
This token is used to verify who has a valid session in the application and whether they have access permission. 
Token generation is performed in the auth file. 
This function copies the provided user data, adds an expiration time, and creates a secure JWT access token signed with the private key and the specified algorithm. The token remains valid for the specified period.

While logging in, the user's existence and verification of password is confirmed using CryptContext and the user's information is returned by generating a token.


Other route files define the classic create, delete, get, and update operations. 
For example, when getting choices, we retrieve them using the matching poll_id. 
This way, choices from the same poll are retrieved together.

In vote-related transactions, we don't hold a poll_id for the poll it belongs to. 
We use the vote's relationship to the choice and the choice's relationship to the poll to ensure matching.


In my first implementation, when I wanted to change a vote, clicking twice increased the vote count by two because the request was sent twice. 
I later implemented the create vote method by changing the choice_id of the existing vote. 
And the problem was solved.


Files in the Schemas folder specify which information must be provided or returned as a response when performing database-related operations. Pydantic handles this process. 
For example, missing username or password information when registering a user can cause inconsistencies in the application. 
Therefore, we can think of this as a control mechanism to ensure that this data is provided correctly.


This file creates an engine and session with SQLAlchemy by taking the database connection from the .env file, defines the base class for ORM models, and starts and runs a secure database session for each operation with the get_db() function.

The environment file contains a connection string that stores database information. 
We can use this information to connect to the database.

The application is started in the main file. 
Requests from the frontend are allowed and the routers to be used are specified.




Let's move on the frontend part. 
First directory is pages. 
Each folder in this directory is a route. 
If the name of file is index.js it doesn't add anything to route. 
For example index.js in pages has things about welcome page and route of welcome page is this. 
And login.js has the things about login and route of this page is localhost/login.


_app.js includes global states like token and user's role. 
When these states change, this file stores these to localStorage or removes them. 
Also, when the route is change, _app.js runs again and controls whether user role and user token exist in local storage or not. 
If they exist, it sets these values to states. 
Thus, we can stay in app when the browser is refreshed or route is change. 
We don't move to welcome page. 
The public and protected pages were defined and we cannot access protected pages without login.
And _app.js pass these states as props to other files. 
And other files can use this states inside them.
 

Other files in pages folder exist for use components. 
Components are reusable structures in pages. 
For example, we have LoginForm component. We return html to define base structure of form. 
Using related css files this form looks beautiful design. 
Also we implement the control mechanisms here and send the request to backend in here. 

How we send request? 
We specify address, type of request like get, post and json as input. 
And a json return us and we can use this json to update interface or trigger a props.

LoginWrapper file act depends on the actions in LoginForm. 
For example it sets the global states which is sent from _app.js or direct to other routes. 

Also RegisterForm and RegisterWrapper has same operations.

We have layout component which exist in top of pages and includes logout. 
This component used in more than one pages.

In PollList component, we fetched all polls from backend and list them. 
Also if user is admin we add "create poll" button.

CreatePollForm and CreatePollWrapper components have same logic like login and register.

In PollDetail component, we show the particular poll and when users click a choice, we update the database for vote model. 
And interface is updated according to updated database.

Finally we have css files for each html structure. 
In these files, we can specify every visual features like size, colour transitions.
